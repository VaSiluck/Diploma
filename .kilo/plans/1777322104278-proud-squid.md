# План нового dashboard для актуального `raw_data` pipeline

## Ключевой вывод

Текущий `dashboard/mm_dashboard.py` не стоит развивать точечными правками. Это 3557 строк монолита под старый контракт `outputs/lcman`, `outputs/final_demo`, `kpi_csv`, а в текущем проекте актуальные артефакты находятся в `outputs/raw_multirate` и `outputs/raw_central_model`.

Оптимальный путь: сделать новый dashboard поверх тонкого dashboard-контракта, а старый файл оставить как legacy/reference для идей UI. Новый dashboard должен быть частью pipeline, а не отдельной демо-страницей, которая сама эвристически восстанавливает данные.

## Что найдено в проекте

| Область | Фактическое состояние |
|---|---|
| Основной pipeline | `01_eda_raw_data.ipynb`, `02_multirate_baseline_raw_data.ipynb`, `03_central_fusion_model_raw_data.ipynb` |
| Актуальный оконный датасет | `outputs/raw_multirate/aligned_multirate_windows.csv` |
| Размер датасета | 10 237 строк, 2 211 колонок, около 258 MB |
| Runs/workloads | 440 runs, 16 workloads |
| Split | `train`: 7 670, `test`: 2 567 |
| Targets | `y_warning`, `y_risk`, `y_anomaly`, `state` |
| Coverage | `kpi_available_share`: 0.9996, `log_available_share`: 0.5681, `has_both_modalities_share`: 0.5679 |
| Baseline metrics | `outputs/raw_multirate/baseline_summary_metrics.json` |
| Model artifacts | Только dry-run: `feature_manifest.json`, `preprocessing_manifest.json`, `dry_run_report.json`, `model_config.json` |
| Per-window predictions | Сейчас отсутствуют: нет `risk_score`, `warning_score`, `pred_state`, `gate`, `central_model_predictions.csv`, `inference_store.csv` |
| Dashboard сейчас | `dashboard/mm_dashboard.py`, старый Streamlit/Plotly monolith, не совпадает с текущим contract |

Критичное ограничение: дизайн `full_ui_design.jpg` предполагает per-window model scores и fusion shares. В текущих outputs этого нет. Значит новый dashboard должен либо получать predictions artifact из `03`, либо явно работать в `contract/target mode`, не выдавая ground truth за prediction.

## Основная рекомендация

Сделать один новый dashboard с тремя режимами, но начать с Python-first реализации на модульном Streamlit или Dash. Данные подготовить через отдельный build-step в `outputs/dashboard/`, чтобы UI не читал 258 MB CSV на каждый rerun.

Рекомендуемый порядок:

1. Сначала создать dashboard data contract и lightweight app на Streamlit/Dash.
2. Достичь функциональности и стабильности на текущих outputs.
3. Если нужен pixel-perfect UI уровня `full_ui_design.jpg`, перенести frontend на React/Vite, не меняя data contract.

Так React не будет рискованной переписью всего сразу: он станет заменяемым UI-слоем поверх уже готовых `outputs/dashboard/*`.

## Вариант 1: Pipeline Cockpit

Назначение: dashboard как часть pipeline. Это самый полезный и реализуемый прямо сейчас вид, потому что он не требует model predictions.

Основной экран:

| Блок | Содержание |
|---|---|
| Artifact status | Проверка `aligned_multirate_windows.csv`, `baseline_summary_metrics.json`, manifests из `raw_central_model` |
| Dataset passport | rows, runs, workloads, train/test, target prevalence |
| Coverage matrix | `log_available`, `kpi_available`, `has_both_modalities`, `kpi_avail_ratio` по split/workload/scenario family |
| Target distribution | `normal`, `warning`, `risk`, `failure_background`; отдельно `y_warning`, `y_risk` |
| Baseline comparison | availability-only, log-only, kpi-only, fused по AP/ROC/F1 |
| Leakage/shortcut warning | Явно показывать, что availability-only заметно сильный shortcut-control |
| Model readiness | Dry-run model shapes, parameter count, forward/loss/gradients status |

Плюсы:

- Реализуемо на текущих артефактах без фейковых оценок риска.
- Хорошо ложится в ВКР: показывает корректность data contract, coverage, split, baseline controls.
- Сразу полезно после каждого запуска notebook `02`/`03`.

Минусы:

- Это не incident-replay UI из картинки.
- Меньше вау-эффекта, больше инженерно-исследовательский контроль качества.

Стек:

| Стек | Оценка |
|---|---|
| Streamlit modular | Лучший first step: минимум инфраструктуры, весь проект уже Python |
| Dash | Лучше callback/replay модель, но больше boilerplate |
| React | Избыточен для первого pipeline cockpit |

## Вариант 2: Incident Replay Console

Назначение: основной демонстрационный UI по мотивам `dashboard/full_ui_design.jpg`. Это целевой экран для защиты/демо, но он должен опираться на настоящий prediction artifact.

Основной экран:

| Блок | Содержание |
|---|---|
| Header cards | Mode, workload/scenario, run, time window, replay step, predicted state, risk score |
| Scenario selector | Normal, warning, risk, modality-missing, hard-negative examples |
| Replay controls | Previous, play/pause, next, step slider, event window scale |
| Risk timeline | `warning_score`, `risk_score`, thresholds, selected window, fail/event anchor, missing modality zones |
| Right summary | current risk, confidence, predicted state, fusion shares, explanation |
| Log evidence | top templates/patterns, counts, deltas vs baseline context, log excerpt |
| KPI evidence | CPU/memory/disk/network cards, top KPI driver deltas, missingness explanation |
| Baseline comparison | current model vs log-only/fused/availability control for selected window |

Data required:

| Artifact | Required fields |
|---|---|
| `outputs/dashboard/score_timeline.*` | `run_id`, `window_ts`, `warning_score`, `risk_score`, `pred_state`, optional `confidence`, `gate_log_share`, `gate_kpi_share`, `score_source` |
| `outputs/dashboard/replay_cases.*` | `case_id`, `kind`, `run_id`, `focus_window_ts`, `reason`, `source` |
| `outputs/dashboard/log_evidence.*` | `run_id`, `window_ts`, `pattern`, `count`, `delta_vs_context`, `contribution`, `excerpt` |
| `outputs/dashboard/kpi_evidence.*` | `run_id`, `window_ts`, `family`, `host`, `metric`, `value`, `baseline`, `delta`, `signal_level` |

Fallback policy:

| Situation | UI behavior |
|---|---|
| Predictions exist | Full replay mode enabled |
| Predictions absent | Show `Target/Contract mode`, disable model-risk claims, timeline uses `y_warning/y_risk/state` as labels only |
| Gate absent | Hide fusion pie or mark as unavailable, never synthesize fake fusion shares |
| KPI evidence absent | Show coverage and aggregated KPI feature deltas from `aligned_multirate_windows.csv` |

Плюсы:

- Ближе всего к `full_ui_design.jpg`.
- Лучший вид для презентации результата как системы.
- Хорошо показывает multimodal/fallback logic, если `03` создаст inference store.

Минусы:

- Нельзя честно сделать полноценным сейчас без prediction artifact.
- Требует отдельного artifact builder и аккуратной evidence-схемы.
- В Streamlit точное поведение replay будет ограничено rerun-моделью.

Стек:

| Стек | Оценка |
|---|---|
| Streamlit modular | Быстро, достаточно для дипломного demo, но replay/autoplay и CSS хрупкие |
| Dash | Хороший компромисс: callbacks, interval, Plotly, Python-only |
| React + FastAPI/static JSON | Лучший вариант для идеального дизайна и плавного replay, но дороже по реализации |

## Вариант 3: Model Diagnostics Lab

Назначение: экран для анализа модели и научного вывода, а не для оператора. Он показывает, почему модель работает или не работает, где доминируют логи/KPI, где coverage ломает интерпретацию.

Основной экран:

| Блок | Содержание |
|---|---|
| Model card | model name, mode, encoder, embedding dim, parameter count, config |
| Tensor passport | log embedding, log macro/micro, KPI tensor, masks shapes |
| Dry-run health | forward ok, loss finite, gradients ok, loss parts |
| Metrics board | baseline metrics сейчас, central model metrics когда появятся |
| Coverage slices | all, `kpi_available=1`, `has_both_modalities=1`, split/workload slices |
| Modality ablation | log-only, KPI-only, fused, central, availability-only |
| Gate analysis | distribution of log/KPI share, fallback frequency, missing-aware behavior |
| Failure cases | top false positives/false negatives, hard negatives, proxy-anchor caveats |

Плюсы:

- Лучшая поддержка ВКР-аргументации.
- Может работать частично уже сейчас на dry-run manifests и baseline summary.
- Не перегружает replay UI научными таблицами.

Минусы:

- Не заменяет основной демонстрационный dashboard.
- Нужны future artifacts для полноценного model comparison: `central_model_metrics`, `ablation_metrics`, `gate_analysis`, `predictions`.

Стек:

| Стек | Оценка |
|---|---|
| Streamlit | Подходит идеально: таблицы, charts, expanders, markdown |
| Dash | Подойдет, если весь dashboard выбрать на Dash |
| React | Имеет смысл только если уже выбран React для replay console |

## Рекомендуемая итоговая форма

Не делать три отдельных приложения. Сделать один dashboard с тремя страницами:

| Page | Назначение | Статус реализации |
|---|---|---|
| `Pipeline` | Contract, coverage, split, baselines, artifact health | Реализовать первым |
| `Replay` | Incident console по дизайну `full_ui_design.jpg` | Реализовать вторым, честно с fallback без predictions |
| `Model` | Dry-run/training diagnostics, model card, ablations | Реализовать третьим, расширять по мере появления artifacts |

## Data contract для dashboard

Ввести отдельный слой `outputs/dashboard/`. UI читает только его. Notebook outputs остаются источниками, но не UI API.

Минимальные артефакты:

| Artifact | Источник | Назначение |
|---|---|---|
| `dashboard_manifest.json` | build step | версии, пути, timestamps, warnings, режимы доступности |
| `artifact_contract.csv` | build step | required/optional artifacts, found/missing |
| `run_index.csv` или `.parquet` | `aligned_multirate_windows.csv` | workload/scenario/run summary, split, states, coverage |
| `timeline_thin.csv` или `.parquet` | `aligned_multirate_windows.csv` | только ключевые timeline columns без 2160 KPI features |
| `baseline_metrics.csv` | `baseline_summary_metrics.json` | таблица baseline comparison |
| `model_health.json` | `raw_central_model/*.json` | dry-run/model config/preprocessing status |
| `score_timeline.csv` или `.parquet` | future predictions или explicit target mode | replay risk/warning scores |
| `replay_cases.csv` | build step | auto-picked cases для demo |
| `evidence_log.csv` | build step | lightweight log evidence per case/window |
| `evidence_kpi.csv` | build step | lightweight KPI evidence per case/window |

Правила:

- UI app не должен писать в `outputs/*`.
- Все записи делает только `dashboard/build_artifacts.py` или отдельный notebook cell.
- Если per-window predictions отсутствуют, `dashboard_manifest.json` должен содержать `score_mode: target_only` или `score_mode: unavailable`.
- Нельзя синтезировать `risk_score` из `y_risk` и показывать как prediction.
- Для больших таблиц использовать column projection и предварительный thin layer.

## Архитектура файлов

Рекомендуемая структура для Python-first варианта:

```text
dashboard/
  README_DASHBOARD.md              # только если потребуется явно документировать запуск
  app.py                           # entrypoint, page routing, session state
  build_artifacts.py               # offline builder для outputs/dashboard
  config.py                        # paths, thresholds, labels, colors
  contracts.py                     # schema checks, DataContractError
  data/
    loaders.py                     # read current pipeline artifacts
    transform.py                   # thin timeline, run index, case picking
    evidence_logs.py               # log evidence builder
    evidence_kpi.py                # KPI evidence builder from feature columns
  charts/
    timeline.py
    coverage.py
    metrics.py
    kpi.py
  ui/
    layout.py
    cards.py
    pipeline_page.py
    replay_page.py
    model_page.py
    styles.css
  legacy_mm_dashboard.py           # optional rename/copy only if implementation needs preserving old file
```

Если выбран React stack:

```text
dashboard_api/
  build_artifacts.py
  server.py                        # optional FastAPI, можно заменить static files
dashboard_web/
  package.json
  src/
    pages/Pipeline.tsx
    pages/Replay.tsx
    pages/Model.tsx
    components/*
    charts/*
```

React стоит выбирать только после фиксации `outputs/dashboard` contract. Иначе frontend будет строиться на песке.

Сохранить идеи, но не структуру:

Не переносить:

| Не переносить | Причина |

## План реализации после утверждения

### Этап 1. Dashboard contract

Цель: отделить UI от тяжелых notebook outputs.

Работы:

1. Создать `dashboard/build_artifacts.py`.
2. Читать `outputs/raw_multirate/aligned_multirate_windows.csv` column-projection способом.
3. Читать `baseline_summary_metrics.json` и `raw_central_model/*.json`.
4. Сохранить `outputs/dashboard/dashboard_manifest.json`.
5. Сохранить `run_index`, `timeline_thin`, `baseline_metrics`, `model_health`.
6. Зафиксировать `score_mode`:
   - `prediction` если есть predictions artifact;
   - `target_only` если используется только target state;
   - `unavailable` если replay score невозможен.

Acceptance criteria:

- Builder работает без старых путей.
- Builder не требует `outputs/lcman`, `outputs/final_demo`, `kpi_csv`.
- UI может загрузить только `outputs/dashboard/*`.
- Manifest явно сообщает, какие режимы dashboard доступны.

### Этап 2. Pipeline page

Цель: первая полезная версия dashboard на текущих данных.

Работы:

1. Создать новый app entrypoint.
2. Реализовать artifact status cards.
3. Реализовать dataset passport.
4. Реализовать coverage charts по workload/split/state.
5. Реализовать baseline comparison table/charts.
6. Реализовать model dry-run health panel.

Acceptance criteria:

- Dashboard запускается на текущем проекте.
- Показывает 10 237 rows, 440 runs, 16 workloads.
- Показывает отсутствие predictions без падения.
- Нет claims о model risk score, если score artifacts отсутствуют.

### Этап 3. Replay page

Цель: приблизиться к `full_ui_design.jpg` функционально и визуально.

Работы:

1. Реализовать replay layout: header, controls, timeline, evidence, right summary.
2. Реализовать target-only timeline fallback.
3. Добавить auto-picked cases:
   - warning/risk case;
   - normal case;
   - missing-log or missing-modality case;
   - hard-negative case, если поле доступно.
4. Реализовать log evidence на `log_text` и `macro/micro` counters.
5. Реализовать KPI evidence из KPI feature columns по top delta/variance/availability.
6. Если появится predictions artifact, включить full prediction replay mode.

Acceptance criteria:

- В target-only mode UI не имитирует confidence/gate.
- При наличии predictions тот же UI переключается в prediction mode.
- Нет чтения 2160 KPI columns в UI runtime, только precomputed evidence.

### Этап 4. Model page

Цель: связать dashboard с `03_central_fusion_model_raw_data.ipynb`.

Работы:

1. Показать `model_config.json`.
2. Показать tensor shapes из manifests.
3. Показать `dry_run_report.json`.
4. Подготовить slots для future full-training artifacts:
   - `central_model_metrics`;
   - `central_model_predictions`;
   - `ablation_metrics`;
   - `gate_analysis`;
   - `model_card`.

Acceptance criteria:

- Current dry-run artifacts отображаются полностью.
- Missing future artifacts отображаются как pending, не как error.

### Этап 5. UI polish

Цель: приблизить UI к `full_ui_design.jpg` без раздувания Python-кода.

Работы:

1. Вынести CSS в `dashboard/ui/styles.css`.
2. Стабилизировать карточки, spacing, typography, colors.
3. Сделать responsive layout: desktop first, mobile/tablet не ломаются.
4. Минимизировать `unsafe_allow_html`: использовать только для контролируемых cards, где Streamlit не хватает.
5. Если Streamlit CSS станет хрупким, перейти на Dash или React, используя тот же `outputs/dashboard` contract.

Acceptance criteria:

- Нет CSS на 500 строк внутри Python-функции.
- Main app остается коротким coordinator-файлом.
- UI не зависит критически от старых Streamlit internal selectors.

## Риски и решения

| Риск | Решение |
|---|---|
| Нет per-window model scores | Ввести `score_mode`; не делать fake prediction; добавить future `score_timeline` contract |
| Большой CSV 258 MB | Precompute thin artifacts, column projection, cache by mtime |
| Текущий dashboard пишет файлы из loader | Новый app read-only, запись только в builder |
| Смена стека затянет работу | Сначала data contract, затем UI; React только после стабилизации contract |
| Дизайн Streamlit не дотянет до картинки | Оставить миграционный путь на React/Dash без изменения data layer |
| Старые артефакты могут случайно попасть в выводы | Запретить `outputs/lcman`, `outputs/final_demo`, `kpi_csv` в новом loader |
| Availability shortcut исказит интерпретацию | Отдельно показывать availability-only baseline и coverage warnings |
| Proxy anchors могут выглядеть как true failures | В UI явно маркировать anchor policy и ограничения |

## Решение, которое я рекомендую принять

Реализовать новый dashboard как `Streamlit modular first` с тремя страницами: `Pipeline`, `Replay`, `Model`.

Приоритет реализации:

1. `outputs/dashboard` contract и builder.
2. `Pipeline` page, потому что она полностью работает на текущих outputs.
3. `Replay` page в `target-only` mode плюс готовность к predictions.
4. `Model` page с dry-run diagnostics.
5. После появления real predictions из `03` включить full replay mode.
6. Если потребуется максимальное совпадение с `full_ui_design.jpg`, перенести только frontend на React/Vite, оставив `outputs/dashboard` contract без изменений.

Главное правило: dashboard должен честно отражать состояние pipeline. Если модель еще не обучена и prediction store отсутствует, UI обязан показывать это как ограничение, а не дорисовывать красивый риск-график из targets.
