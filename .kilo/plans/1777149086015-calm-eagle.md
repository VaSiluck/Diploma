# План notebook `02_multirate_baseline_raw_data.ipynb`

## Глобальный контекст

Этот план продолжает пересборку цепочки notebook на правильном датасете `raw_data/`.

Источник методической логики: `lcman/notebooks_rebuild_map.md`, особенно раздел про старый `02_multimodal_pipeline_baseline.ipynb`.

Источник фактических решений по новому датасету: выполненный notebook `01_eda_raw_data.ipynb`.

Старые численные результаты, пути `log_csv/`, `kpi_csv/`, `outputs/final_demo/` и старую реконструкцию provenance не переносить.

Новый `02` должен быть не notebook про максимальное качество модели, а воспроизводимый baseline-контур: strict pairing, multi-rate windows, dual targets, data contract, anti-leakage split, smoke-модели и честная coverage-aware интерпретация.

## Главная цель

Создать notebook `02_multirate_baseline_raw_data.ipynb` в корне проекта.

Notebook должен:

- взять правила из `01_eda_raw_data.ipynb` и превратить их в pipeline contract;
- собрать оконный мультимодальный датасет из `raw_data/`;
- использовать единицу наблюдения `run_id = workload/scenario`;
- строить признаки логов из scenario-level raw logs `mapred_logs/<scenario>.log`;
- строить KPI-признаки из `kpis/<scenario>/instruments/<host>/<metric>`;
- сформировать dual-target постановку `y_warning` и `y_risk` с честным описанием anchor/proxy;
- проверить shortcut через `availability-only` baseline;
- обучить минимальные smoke-baselines `availability-only`, `log-only`, `kpi-only`, `fused`;
- сохранить data contract для будущего `03_lcman_lite_raw_data.ipynb`.

## Степень свободы агента

Агенту реализации разрешается принимать локальные решения после первичного запуска диагностик в notebook.

Разрешенные локальные решения:

| Область | Что можно выбирать на месте | Условие |
|---|---|---|
| Micro window | `10s` или `30s` как основная шкала | Выбор обосновать window report и балансом target |
| Macro window | `1min`, `5min` или оба как log context | 5min не делать единственной target grid, если большинство runs collapsed |
| Failure anchor | explicit raw-log marker, keyword anchor, run-end proxy или fallback policy | Нельзя выдавать proxy за истинный момент отказа |
| Target horizons | warning/risk горизонты в секундах или долях длительности run | Нужно сохранить достаточно положительных и отрицательных окон |
| KPI parsing | full long parse, streaming aggregation, chunking или capped series set | Нужно сохранить `host/metric/series` идентичность и report о selection |
| KPI feature cap | top-K series по availability/variance или full set | Cap и критерии выбора записать в markdown и schema report |
| Log features | regex raw parser, simple template normalization, TF-IDF text или counts-only fallback | Не использовать scenario name/failure family как predictive feature |
| Split | holdout by workload, group split by run_id, family-aware diagnostics | Split должен избегать одного run в train/test и показать leakage report |
| Smoke models | LogisticRegression, SGDClassifier, HistGradientBoosting или другой lightweight sklearn baseline | Модели должны оставаться smoke-check, а не model zoo |
| Artifact format | CSV как основной contract, optional Parquet/cache для тяжелых промежуточных данных | `aligned_multirate_windows.csv` должен быть создан, если размер практически приемлем |

Агент должен явно фиксировать каждое существенное решение в markdown. Если данные делают изначальную идею некорректной, лучше честно изменить локальное правило, чем механически выполнить план.

## Непереговорные ограничения

- Не использовать старые пути `log_csv/`, `kpi_csv/`, `outputs/final_demo/`.
- Не соединять workload-level `parsed_log/labeled.csv` с KPI scenario как будто там есть строгий `scenario`.
- Не включать `scenario`, `failure_family`, `scenario_type`, `workload`, `run_id`, `path` в predictive features.
- Не скрывать non-STRICT runs и parsing errors.
- Не делать deep learning и не строить LCMAN в `02`.
- Не оптимизировать качество любой ценой; `02` должен доказать корректность baseline-контура.
- Не трактовать `availability-only` как финальную модель; это контроль shortcut.
- Не делать silent fallback на legacy artifacts.

## Структура notebook

### 1. Постановка `02`: EDA -> pipeline rules

Содержание:

- объяснить, что `02` следует из `01_eda_raw_data.ipynb`;
- кратко сослаться на `lcman/notebooks_rebuild_map.md`;
- зафиксировать, что задача `02` - baseline protocol, а не максимизация качества;
- вывести таблицу `EDA observation -> pipeline rule -> mitigated risk`.

Обязательные правила в таблице:

| EDA observation | Pipeline rule | Risk mitigated |
|---|---|---|
| `run_id = workload/scenario` | Все join/window/split делать по `run_id` | Неверный provenance |
| `labeled.csv` без scenario | Raw logs являются run-level источником | Leakage между scenario |
| KPI files whitespace + repeated headers | Нужен custom parser | Ошибки KPI чтения |
| Median KPI interval 1s | Micro windows 10s/30s | Потеря динамики |
| 5min collapses most runs | 5min только macro context | Потеря target resolution |
| Label rare | PR-AUC primary | Accuracy illusion |
| Coverage imperfect | availability-only baseline | Shortcut detection |
| Repeated families/workloads | group-aware split | Family/workload leakage |

Локальный вывод: pipeline является прямым следствием EDA.

### 2. Inventory и inclusion policy

Содержание:

- заново выполнить lightweight scan `raw_data/`, не полагаясь только на сохраненные outputs `01`;
- построить `run_inventory_df` на уровне `(workload, scenario)`;
- определить `strict_path_pair`, `has_raw_log`, `has_kpi_measurements`, `parsed_label_available`;
- явно выделить STRICT, LOG_ONLY, KPI_ONLY, MISSING_OR_AMBIGUOUS;
- выбрать primary dataset.

Рекомендуемое primary правило:

- включать STRICT runs с raw `mapred_logs/<scenario>.log` и KPI measurements;
- не требовать `parsed_log/labeled.csv` для включения raw-log baseline;
- `nweight` можно включать, если target строится по scenario/proxy и raw logs, но пометить `parsed_label_available=0`;
- non-STRICT runs исключить из supervised smoke baseline, но показать в report.

Агент может выбрать более строгую policy, например exclude `nweight`, если target-логика зависит от parsed labels. Это решение должно быть явно описано и отражено в `target_policy_report.csv`.

Таблицы:

- `run_inventory_df`;
- `pairing_audit_used_df`;
- inclusion/exclusion counts по workload/family/status.

Графики:

- bar chart included/excluded runs по workload;
- stacked bar pair status;
- family coverage matrix.

### 3. Raw log loader и run-level log features

Содержание:

- читать `raw_data/<workload>/mapred_logs/<scenario>.log`;
- парсить timestamped строки формата Spark/YARN regex: `yy/mm/dd HH:MM:SS LEVEL component: message`;
- сохранять `workload`, `scenario`, `run_id`, `timestamp`, `level`, `component`, `message`;
- считать raw log duration, event count, parse success share;
- формировать micro и macro log features.

Обязательные признаки:

- `log_available`;
- `micro_log_count`, `macro_log_count`;
- `micro_log_rate`, `macro_log_rate`;
- `micro_unique_components`, `macro_unique_components`;
- `micro_warn_count`, `macro_warn_count`;
- `micro_error_count`, `macro_error_count`;
- keyword counts для `error`, `exception`, `failed`, `killed`, `lost`, `timeout`, `suspended`, `blacklist`, `retry`;
- `log_text` как агрегированный текст macro window, с ограничением длины.

Разрешенные локальные решения:

- добавить simple template normalization raw messages: заменить числа, UUID, IP, paths, application/container ids;
- добавить top raw components/features, если они устойчивы;
- использовать TF-IDF или hashing только внутри sklearn pipeline, не сохранять огромные sparse columns в CSV;
- если raw parser плохо покрывает часть файлов, оставить counts/text fallback и report parse coverage.

Важно: не использовать имя scenario/failure family как текстовую feature. Если raw message содержит очевидный injected marker, это допустимо как часть лога, но надо обсудить leakage risk.

### 4. KPI parser и feature aggregation

Содержание:

- читать `raw_data/<workload>/kpis/<scenario>/instruments/<host>/<metric>`;
- поддерживать metrics `cpustat`, `iostat`, `jvms`, `memstat`, `netstat`, `vmstat`;
- фиксировать unexpected files, например `pgid`;
- пропускать повторные header rows;
- приводить `TimeStamp` к UTC datetime;
- преобразовывать wide tables в long или сразу агрегировать в windows;
- сохранять identity `host`, `metric`, `series`, `value`.

Особенности series:

- `iostat`: series должен учитывать `Device:`;
- `netstat`: series должен учитывать `IFACE`;
- `cpustat`: если много строк на один timestamp без CPU-id, agent может использовать synthetic slot, host-level mean/max или другую документированную агрегацию;
- `jvms`, `memstat`, `vmstat`: series обычно равен имени числовой колонки.

Рекомендуемые KPI stats по micro window:

- count/availability;
- last;
- mean;
- std или robust spread;
- min/max для selected critical series;
- delta между последним и первым значением окна;
- slope, если в окне хватает точек;
- rolling mean/delta на 2-3 micro windows, если это не создает слишком много колонок;
- recency до последней точки KPI.

Разрешенные оптимизации:

- streaming aggregation по файлам вместо полного `kpi_long_df` в памяти;
- feature cap top-K series по availability и variance;
- отдельные aggregate features по `metric/series` across hosts;
- optional cache `kpi_window_features.parquet` при наличии Parquet backend;
- pilot parse на subset для выбора series, затем full pass для selected schema.

Обязательное условие: любое ограничение KPI series должно быть отражено в schema/report, иначе `03` не сможет честно читать contract.

### 5. Run spans, event anchor и target policy

Это самый чувствительный блок. В `01` было показано, что точный `scenario` для parsed labels не восстановлен, поэтому нельзя автоматически брать `Label=1` из `labeled.csv` как failure timestamp конкретного scenario.

Нужно построить честную target policy.

Рекомендуемый порядок:

1. Для каждого run получить `run_start` и `run_end` из raw log timestamps и KPI timestamps.
2. Для failure scenario попытаться найти `explicit_anchor` в raw logs по high-severity level или failure keywords.
3. Если explicit anchor найден и выглядит устойчиво, использовать его как `event_anchor` и `anchor_policy = explicit_raw_log`.
4. Если explicit anchor не найден, использовать conservative proxy: `event_anchor = run_end`, `anchor_policy = run_end_proxy`.
5. Для normal scenario оставить `event_anchor = NaT`, `y_warning = 0`, `y_risk = 0`, `y_anomaly = 0`.
6. Для failure scenario без надежного anchor не утверждать, что proxy является истинным моментом отказа.

Agent может выбрать другой fallback, например `run_start_proxy` для stress scenarios, если первичный анализ показывает, что fault active с начала run. Тогда обязательно:

- показать evidence table;
- разделить `anchor_policy`;
- сравнить target balance по policy;
- не смешивать proxy types без report.

Рекомендуемые initial horizons:

| Target | Стартовое правило | Комментарий |
|---|---|---|
| `y_risk` | последние 30s перед `event_anchor` или последние 25% run, если run короткий | Ближний риск/аномалия |
| `y_warning` | последние 120s перед `event_anchor` или последние 60% run, если run короткий | Предупреждение до риска |
| `y_anomaly` | `scenario_type == failure` и окно в risk/warning зоне или отдельный documented rule | Secondary target |

Agent должен пересчитать class balance. Если target получается вырожденным, разрешается изменить horizons, перейти с 10s на 30s или обучить только тот target, где есть оба класса. Это должно быть явно написано.

### 6. Multi-rate grid и alignment

Содержание:

- выбрать primary `micro_window_sec`: стартово 10s, fallback 30s;
- выбрать `macro_window_sec`: стартово 60s и/или 300s;
- построить window grid по каждому included run;
- window timestamps должны быть UTC и aligned по `run_id`;
- log micro features считать на коротком окне;
- log macro features считать на trailing macro context;
- KPI features считать на micro window с recency/tolerance;
- соединять только по `run_id + window_ts`.

Рекомендуемая semantics:

- micro window: `[window_ts, window_ts + micro_window)`;
- macro context: `[window_ts - macro_window + micro_window, window_ts + micro_window)` или другой trailing rule;
- target timestamp: конец micro window.

Если agent выбирает другую boundary convention, она должна быть описана в markdown и в metadata columns.

Таблицы:

- window grid report;
- rows per run/family;
- target balance by scenario_type/family;
- coverage by window.

Графики:

- distribution windows per run;
- target balance bars;
- example aligned log/KPI/target timeline for 1-2 failure runs.

### 7. Data contract assembly

Содержание:

- объединить identifiers, time, targets, log features, KPI features, coverage flags;
- проверить отсутствие predictive leakage columns в model feature lists;
- заполнить missing values корректно: model pipeline может imputate, а contract должен сохранить missing/availability indicators;
- создать `hard_negative`.

`hard_negative` рекомендуется определять как окно, где:

- `y_warning = 0` и `y_risk = 0`;
- есть `kpi_available` или `log_available`;
- scenario normal или failure run далеко от anchor.

Contract validation должен проверить:

- нет duplicate `(run_id, window_ts, micro_window_sec)`;
- `window_ts` timezone-consistent;
- `run_id` не пустой;
- required columns присутствуют;
- target columns бинарные или documented NaN for unavailable target;
- coverage flags корректны;
- feature columns не являются полностью пустыми;
- identifiers не попадают в model feature matrix.

### 8. Anti-leakage split

Содержание:

- построить `split_group`;
- сделать train/test split с отчетом;
- по возможности оставить validation split или repeated split для устойчивости smoke metrics.

Рекомендуемый порядок split:

1. Primary: holdout by workload, если train/test сохраняют оба класса для `y_warning`.
2. Fallback: `GroupShuffleSplit` по `run_id` со stratification diagnostics по scenario_type/failure_family.
3. Additional diagnostics: family overlap между train/test; если overlap есть, явно назвать это residual leakage risk.

Split report должен содержать:

- rows/windows per split;
- runs per split;
- workload per split;
- family distribution;
- target prevalence;
- coverage prevalence;
- список групп в train/test.

Не включать `split_group`, `workload`, `scenario`, `failure_family`, `scenario_type` в model features.

### 9. Smoke baselines

Цель smoke models - проверить, что contract работает и shortcut контролируется. Не строить model zoo.

Минимальные модели:

| Baseline | Features | Цель |
|---|---|---|
| `availability-only` | `log_available`, `kpi_available`, `has_both_modalities`, `kpi_avail_ratio`, `kpi_recency_sec`, counts of available features | Проверить shortcut через coverage |
| `log-only` | numeric log features плюс optional `log_text` TF-IDF/HashingVectorizer | Проверить вклад логовой модальности |
| `kpi-only` | numeric KPI features и KPI masks | Проверить вклад KPI |
| `fused` | log + KPI + masks | Проверить минимальную мультимодальность |

Рекомендуемые sklearn инструменты:

- `LogisticRegression(max_iter=..., class_weight="balanced")` как основной smoke baseline;
- `SimpleImputer` и `StandardScaler` для numeric features;
- `TfidfVectorizer` или `HashingVectorizer` для `log_text`, если размер позволяет;
- `ColumnTransformer`/`Pipeline` для воспроизводимости;
- fallback to numeric-only log features, если text pipeline слишком тяжелый.

Метрики:

- primary: Average Precision / PR-AUC по `y_warning`;
- secondary: PR-AUC по `y_risk`;
- ROC-AUC только если оба класса представлены;
- precision, recall, F1 на простом threshold или threshold selected on train/validation;
- prevalence baseline;
- metrics by coverage slices.

Coverage slices обязательны:

- all test windows;
- `kpi_available = 1`;
- `has_both_modalities = 1`;
- optional `anchor_policy` slices;
- optional scenario/family slices, если хватает наблюдений.

Если target вырожден или split не содержит оба класса, agent не должен форсировать метрики. Нужно вывести diagnostic table и объяснить, какие условия не выполнены.

### 10. Artifact saving и reports

Содержание:

### 11. Финальная интерпретация для ВКР

Финальный markdown должен прямо ответить:

- был ли собран воспроизводимый multi-rate contract;
- сколько runs/windows вошло в основной contract;
- какие runs исключены и почему;
- какой `micro_window` и `macro_window` выбран;
- как определялись `event_anchor`, `y_warning`, `y_risk`;
- показал ли `availability-only` shortcut риск;
- есть ли benefit у log/KPI/fused smoke baselines относительно availability-only;
- какие leakage risks остаются;
- что именно передается в `03`.

Важно: если fused baseline не превосходит controls, это не провал. Честный вывод может быть: data contract собран, но качество ограничено target proxy, coverage и малой длительностью runs.
